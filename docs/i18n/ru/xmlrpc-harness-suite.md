# Обвязки XML-RPC для проверки потоков данных

[English](../../xmlrpc-harness-suite.md) · **Русский** · [Español](../es/xmlrpc-harness-suite.md) · [简体中文](../zh-CN/xmlrpc-harness-suite.md) · [All languages](../README.md)

Этот набор проверяет шесть локальных функциональных потоков данных в
[etnt/xmlrpc](https://github.com/etnt/xmlrpc), закреплённом на коммите
`fb46463b2acadf164ec534d9e2033e194341c507`. Для каждой поверхности используются
одна и та же цель, начальный корпус, начальное значение ГПСЧ и бюджет мутаций
при отключённом необязательном слое Gleam, при его работе в режиме наблюдения
или при управлении мутациями и сохранением входов в корпусе.

Входы — это байты полезных данных, ограниченные 512 байтами. Обвязка получает из
этих байтов значения XML-RPC с заданными ограничениями и конструирует полные
сообщения с фиксированными XML-тегами. В корректных потоках имена методов и
членов структур — фиксированные атомы; при проверке валидации используются
фиксированные некорректные варианты. Строковые значения состоят из печатных
символов ASCII, полученных из полезных данных. Мутации байтов не превращаются в
XML-разметку или новые атомы. В потоках с типизированными значениями первый байт
по модулю восьми выбирает целое число, логическое значение, строку, число двойной
точности, дату, значение base64, массив или структуру; пустой вход выбирает целое
число с пустыми полезными данными. Контейнеры содержат не более четырёх дочерних
элементов и вложены не более чем на два уровня. Методы — `echo` и `sum`; имена
членов структур — `value`, `count`, `enabled` и `items`. Независимый построитель
XML экранирует все пять предопределённых сущностей XML.

## Входные поверхности и реализованные пути

Каждое имя выбирает `efz_xmlrpc_<name>_target:run/1`. Тонкие целевые обвязки
используют общий файл
[`efz_xmlrpc_flow.erl`](../../../examples/xmlrpc/efz_xmlrpc_flow.erl); отдельные
точки входа позволяют относить покрытие, корпус и результаты к каждому потоку.

| Имя | Фактический поток данных | Проверяемый контракт | Границы проверки |
| --- | --- | --- | --- |
| `call` | Полезные данные → вручную сформированный XML `methodCall` → `xmlrpc_decode:payload/1` | Декодированные метод и параметры равны сформированному вызову | Фиксированные имена методов и типизированные значения с заданными ограничениями; произвольная грамматика XML не проверяется |
| `response` | Полезные данные → вручную сформированный XML `methodResponse` с одним параметром → декодер | Декодированное значение ответа равно сформированному значению | Успешные ответы содержат ровно один параметр |
| `fault` | Полезные данные → вручную сформированный XML ошибки → декодер | Код и строка ошибки равны сформированным значениям | Целочисленные коды с заданными ограничениями и печатные строки |
| `roundtrip` | Полезные данные → `{call, echo, [TypedValue]}` → `xmlrpc_encode:payload/1` → декодер | Декодированный вызов равен значению, переданному кодировщику | Один параметр с поддерживаемым значением в заданных пределах |
| `dispatch` | Полезные данные → закодированный вызов → декодер → локальная фикстура echo/sum → закодированный ответ → декодер | Итоговый ответ соответствует ожидаемому результату фикстуры | Фикстура внутри процесса; без внешней службы RPC |
| `encoder_validation` | Полезные данные → заведомо неподдерживаемые значения Erlang → кодировщик | `{error, Reason}` записывается как отклонение, любой успех кодировщика — как принятие | Конечный набор случаев валидации; ожидаемые ошибки не являются дефектами |

Декодер отклоняет XML для пустого успешного ответа (`{response, []}`).
Для этого случая успешный цикл кодирования/декодирования не проверяется.
Ошибки валидации кодировщика — ожидаемые результаты API, записываемые в
`target_rejected`; это не дефекты и не аварийные завершения.
Случаи валидации охватывают некорректный кортеж полезных данных, неподдерживаемое
значение map, строковое имя члена, некорректный член, неподдерживаемый атом в
массиве, нестроковый текст ошибки, два параметра ответа и имя метода в виде
списка. Наблюдение фиксирует, совпадает ли результат с ожидаемой ошибкой;
исключения передаются дальше.

Диспетчеризация выбирает echo при чётной длине полезных данных и sum при
нечётной. Sum использует не более первых четырёх байтов полезных данных,
вычитает 128 из каждого байта и сравнивает ответ фикстуры с независимо
вычисленной суммой.

Фикстура диспетчеризации не вызывает `xmlrpc_http`, серверный код или код HTTP
и не открывает сокеты. Она проверяет кодирование, декодирование и небольшое
локальное решение приложения. Набор не устанавливает поведение HTTP-транспорта,
слушателей, жизненных циклов обратных вызовов, одновременных запросов,
произвольной грамматики XML и полное соответствие XML-RPC. Существующий
[адаптер декодера сырых XML-данных](examples/xmlrpc/README.md) остаётся отдельным
примером с другим входным форматом и моделью.

## Подготовка зависимости

Выполняйте команды из корня репозитория с Erlang/OTP 27 или новее, Rebar3 и
OTP `xmerl`:

```sh
git clone --no-checkout https://github.com/etnt/xmlrpc.git _build/xmlrpc-dependency
git -C _build/xmlrpc-dependency checkout --detach fb46463b2acadf164ec534d9e2033e194341c507
export ERL_FLAGS='+S 2:2'
escript examples/xmlrpc/prepare_flows.escript
rebar3 compile
```

Подготовка компилирует `xmlrpc_encode`, `xmlrpc_decode` и `xmlrpc_util` в
`_build/xmlrpc-example/dependency-ebin`. Она отклоняет другой коммит и изменения
любого из этих трёх исходных файлов или `src/log.hrl`. Цели примера и
вспомогательный код компилируются через существующий каталог исходников Rebar3
`examples/xmlrpc`. Для обычной сборки не нужны компилятор Gleam или
сгенерированные BEAM-файлы модели.

Если рабочая копия находится в другом месте, передайте её путь скрипту
подготовки и укажите тот же путь в параметре `--source` исполнителя:

```sh
escript examples/xmlrpc/prepare_flows.escript /path/to/pinned-xmlrpc
```

## Запуск без Gleam

```sh
ERL_FLAGS='+S 2:2' escript scripts/xmlrpc_suite.escript \
  --surface all --mode off --iterations 500 --seed 424242 \
  --source _build/xmlrpc-dependency --out _build/xmlrpc-flows-off
```

Выходные каталоги должны быть новыми. Каждая ячейка поверхности/режима
запускается в новой VM со своим корпусом и состоянием покрытия. Начальный корпус
включает пустой вход, специальные символы XML, двоичные байты и граничный случай
512 байт. Для выбора одного пути используйте, например, `--surface dispatch`.
Исполнитель принимает `--surface all|NAME`,
`--mode all|off|observation_only|guided`, `--iterations N`, `--seed N`,
`--profile default|gleam`, `--source PINNED_CHECKOUT` и `--out NEW_DIR`.

## Запуск всех трёх режимов

```sh
export ERL_FLAGS='+S 2:2'
export GLEAM_BIN=/path/to/gleam-1.10.0
rebar3 as gleam compile
escript scripts/xmlrpc_suite.escript --surface all --mode all --profile gleam \
  --iterations 500 --seed 424242 --source _build/xmlrpc-dependency \
  --out _build/xmlrpc-flows-three-modes
```

| Режим | Доля структурированных мутаций | Приём в корпус | Необязательная модель |
| --- | --- | --- | --- |
| `off` | 0% | Структурное покрытие | Нет |
| `observation_only` | 0% | Структурное покрытие; наблюдения записываются | Существующая модель Gleam `efz_term_model` |
| `guided` | 30% | Структурное покрытие или новые семантические признаки | Та же модель термов с `efz_xmlrpc_flow_adapter` |

Режим наблюдения сохраняет базовую последовательность мутаций и потребление
значений ГПСЧ. Управляемый режим меняет выбранные мутации и впоследствии может
изменить корпус. Адаптер наблюдает результаты с помощью существующей общей
модели термов и признаков с конечными множествами значений для типа результата,
диапазона количества элементов, диапазона размера закодированных данных и
совпадения с ожидаемой ошибкой кодировщика. Структурированные операции заменяют
селектор, добавляют байт или выбирают образец в заданных пределах. Адаптер не
реализует заново XML-парсер или кодировщик на Gleam. Режим off работает без
модели.

Во всех режимах выполняются одни и те же контракты обвязки. Оракул
семантического слоя отключён: сохранение нового семантического признака не
создаёт находку о нарушении свойства. Неожиданные исключения и таймауты требуют
исследования; они не считаются автоматически подтверждёнными дефектами
библиотеки. Это набор функциональных интеграционных проверок, а не поиск
известной ошибки или доказательство того, что один режим находит больше
дефектов.

## Покрытие и выходные данные

Нативное покрытие включает только выбранные модули закреплённой версии XML-RPC:
`xmlrpc_encode`, `xmlrpc_decode` и `xmlrpc_util`, используемые каждой
поверхностью. Внутренний код парсера OTP `xmerl`, вспомогательный код потоков,
локальная фикстура диспетчеризации, адаптер, наблюдатель и код EFZ исключены.
Знаменатель включает все исполняемые строки каждого выбранного модуля, в том
числе пути, недостижимые в выбранном потоке данных.

Каждый каталог `<surface>/<mode>/` содержит:

- `initial-corpus/`, `config.term` и `identity.term`: точные байты начальных
  входов, настройки кампании, идентификаторы исходников и сборок, OTP/ERTS и
  вспомогательного кода.
- `target-beams/` и `artifacts.term`: сборки для нативного покрытия выбранных
  библиотечных модулей.
- `report.term`, `snapshot.term` и `summary.term`: результаты кампании,
  покрытие, корпус, временные показатели, семантическая и структурированная
  статистика, число вызовов.
- `report.etf`: двоичный отчёт без потерь. Текстовые термы в UTF-8 используют
  явные теги `{efz_runtime_identity, Kind, Text}` для идентификаторов среды
  выполнения, чтобы `file:consult/1` мог читать отчёты, а двоичные байты полезных
  данных оставались неизменными.
- `corpus/` и `crashes/`: сохраняемые артефакты EFZ для обычного повторного
  воспроизведения.

Корневой выходной каталог содержит `matrix.term`, сводные результаты,
`summary.csv` и `comparisons.csv`. При сравнении соответствующие поверхности
сопоставляются с запуском off; проверяются хеш начального корпуса, начальное
значение ГПСЧ и запрошенный бюджет.

`target_invocations`, `target_accepted` и `target_rejected` включают калибровку
и мутации. Учёт вызовов сверяет их с бюджетом выполнений. Для
`encoder_validation` ожидаемые возвраты `{error, Reason}` учитываются в
`target_rejected`. `discoveries` и `corpus_equivalent_rejections` описывают
приём в корпус независимо от принятия или отклонения на уровне API. Покрытие
при калибровке отделено от `mutation_new_coverage_lines`, чтобы покрытие
начальных входов не отражалось как прогресс мутаций.

Столбцы времени описывают одну кампанию на ячейку. Они не выделяют затраты
наблюдателя или адаптера, а управляемый режим использует другую входную
нагрузку. Один запуск не позволяет утверждать превосходство в скорости,
покрытии или обнаружении дефектов.

## Регрессионные проверки

Необязательная зависимость должна быть подготовлена и присутствовать в пути
загрузки кода тестовой VM:

```sh
ERL_FLAGS='+S 2:2 -pa _build/xmlrpc-example/dependency-ebin' \
  rebar3 eunit --module=efz_xmlrpc_flow_tests
ERL_FLAGS='+S 2:2 -pa _build/xmlrpc-example/dependency-ebin' \
  GLEAM_BIN=/path/to/gleam-1.10.0 \
  rebar3 as gleam eunit --module=efz_xmlrpc_flow_tests
```

Целевые проверки охватывают общие контракты, обработку полезных данных в
заданных пределах, воспроизводимые структурированные операции, настройки набора
и необязательные пути наблюдения. Результаты кампаний остаются источником
измеренных показателей.

Локальная проверка завершила 18 кампаний по 500 мутаций: 9 000 мутаций и 270
калибровок. Получено 7 725 принятых вызовов потока и 1 545 ожидаемых отказов
кодировщика, без исключений, тайм-аутов и инфраструктурных сбоев. Сохранённые
входы, покрытие и статистика мутаций совпали между off и observation-only для
всех шести поверхностей. Всё наблюдаемое структурное покрытие достигнуто при
калибровке; в этом ограниченном запуске мутации не добавили строк. Guided для
dispatch сохранил 17 элементов корпуса против 15 без слоя, без прироста покрытия.
Это подтверждает выполнение потоков, но не преимущество guided.

Общие [CSV-результаты](../../xmlrpc-harness-suite-validation/summary.csv),
[идентификаторы сборок](../../xmlrpc-harness-suite-validation/identities.term) и
[манифест воспроизведения](../../xmlrpc-harness-suite-validation/manifest.json)
содержат данные запуска. Полные отчёты остались в локальном дереве `_build`,
их хеши и точная команда воспроизведения записаны в манифесте. Параллельно
выполнялись другие локальные проверки, поэтому замеры времени не выделяют
накладные расходы слоя.
